# 00. 공통 백엔드 (Supabase) — B·C 공통

B(Flutter 한 벌)와 C(Next.js 웹 + Kotlin 안드로이드)가 같이 쓰는 서버 설계다.

## 0. 읽는 법

- 규칙 내용은 모두 `spec.md` 를 따른다. 이 문서는 규칙을 옮겨 적지 않고 "spec.md §5.9.7" 식으로 가리킨다. 표 안의 `§` 는 모두 spec.md 의 장 번호다.
- **(새로 정함)**: 이 문서에서 새로 정한 설계다. 절 제목에 붙어 있으면 그 절 전체가 새로 정한 것이다.
- **〔바뀔 수 있음〕**: spec 의 [추정]·[미확인] 규칙이나 spec 이 **"앱에서 확인 필요"** 로 표시한 값을 구현하는 곳이다. 앱 확인(spec.md §9) 결과에 따라 바뀔 수 있다. 서버 쪽은 9장, 모든 클라이언트가 같이 쓰는 1차 구현은 10장에 모았다.
- 이름: 테이블·열 이름은 구현 때 그대로 쓸 수 있게 적었다. 서버 함수(RPC)는 `R1`~`R15`(확장 범위는 `R16`~`R28`) 번호와 우리말 이름으로만 부르고, 실제 함수 이름은 구현 때 정한다.
- **확장 범위**: spec.md §1 이 원본 기능 전부로 넓어졌다. 확장 기능(`spec-ext.md` 12~19장) 때문에 바뀌는 서버 설계는 **11장**에 모았다. 1~10장은 spec.md 범위(이전 MVP)의 설계이고, 11장이 덮어쓰는 곳은 11장을 따른다.
- spec 은 "원본 우선 방침"(spec.md §0)을 따른다. 이 문서도 원본에서 불가능한 것(서버 전용 처리, 실제 결제)만 원본과 다르게 둔다.

## 1. 전제 (새로 정함)

| 항목 | 정한 것 |
|---|---|
| 데이터 | Supabase 의 Postgres 하나. 진실의 원천은 이 DB다 |
| 인증 | Supabase 이메일·비밀번호 로그인 |
| 파일 | Supabase 저장소(비공개 버킷 하나) |
| 보안 경계 | **행 단위 보안(RLS) 하나뿐이다.** 트리거·RPC 검사는 데이터를 일관되게 지키려는 것이지 보안 경계가 아니다. 협업(spec-ext.md §16)을 넣으면 공유 목록·팀 권한도 RLS 가 판정한다 (11.3) |
| 서버 코드 | DB 함수(트리거, RPC)만 쓴다. 관리자 권한이 꼭 필요한 탈퇴 하나만 서버 함수(Edge Function)로 둔다 |
| 반복·알림 계산 | **전부 클라이언트의 공통 규칙 모듈이 한다** (spec.md §7.6 "반복 계산의 위치"). 원본도 앱 안에서 계산한다. 서버 함수는 클라이언트가 계산한 결과를 **원자적으로 저장**하고 **형식 검사만** 한다 |
| 공휴일 | 한국 공휴일 표를 클라이언트에 내장한다 (spec.md §5.9.1). 서버는 공휴일을 모른다 |
| 서버 푸시 | 쓰지 않는다 (spec.md §7.12, §10) |

공통 규칙 모듈이 계산하는 것: 회차 펼치기(기준일 −30일 ~ +60일, spec.md §5.13.1), `nextOccurrenceAt`, 반복 완료 처리(§5.9.7), 날짜를 바꿀 때 규칙 다시 만들기(§5.9.4), 범위 판정과 범위별 처리(§5.9.8), 지난 회차 정리(§5.1), 체크리스트 자동 완료 판정과 진행률(§5.5, §4.5), 아젠다 거름(§5.12), 알림 시각(§5.10). 각 플랫폼 문서의 "공통 규칙" 절을 본다.

### 1.1 저장소 폴더 (새로 정함)

```
supabase/
  migrations/      테이블 → 트리거 → RLS → RPC 순서의 SQL 파일
  seed.sql         plan_limits 기본 행 (무료·Pro)
  tests/           RLS·트리거·RPC SQL 테스트
  functions/       탈퇴 함수 하나 (E1)
shared-testdata/   spec 예시표를 옮긴 테스트 케이스(JSON). 모든 클라이언트가 같은 파일로 테스트한다
shared-data/       holidays-kr.json — 한국 공휴일 표. 모든 클라이언트가 빌드 때 넣는다 (spec.md §5.9.1)
```

`shared-testdata/` 의 각 케이스에는 근거 장 번호(예: `§5.9.6 A`)를 넣는다. 케이스 값은 spec 예시표에서 가져오고, 이 문서에는 옮기지 않는다.

### 2.1 모든 테이블 공통 열

| 열 | 뜻 | 근거 |

### 2.3 `tasks` 열

| 묶음 (spec) | 열 |
|---|---|
| 식별·연결 (§4.5) | `list_id`, `parent_id`, `repeat_origin_id` |
| 내용 (§4.5) | `title`, `content`, `kind`, `tags text[]`, `priority`, `progress` |
| 일정 (§4.5, §7.1) | `start_local`, `due_local`(시간대 없는 벽시계 시각), `time_zone`, `is_all_day`, `is_floating`, `repeat_rule`, `repeat_basis`, `repeat_first_date`, `ex_dates date[]`, `reminders text[]`, `next_occurrence_at` |
| 상태 (§4.5) | `status`, `completed_at`, `deleted_at`, `is_collapsed`, `pinned_at`, `sort_order` |

- **시각 저장 (새로 정함)**: 시작·마감은 모두 "벽시계 시각 + `time_zone`" 한 가지 방식으로 둔다. 시간 지정 할 일의 실제 시점은 둘을 합쳐 계산한다. spec.md §7.1 의 두 표현(오프셋 붙은 시각 / 오프셋 없는 시각)은 이 한 쌍에서 둘 다 만들 수 있다. 기간 조회는 하루씩 넓혀 읽고 클라이언트가 다시 거른다.
- `status` 는 `open` / `completed` / `abandoned` 문자열로 둔다 (§4.5, §7.6 의 대응을 따름).
- `repeat_basis` 는 API 이름(`due`/`completion`/`dates`/`preset`)으로 둔다 (§5.9.5 의 대응표).
- `repeat_rule` 은 원본 형식 그대로의 문자열이다: RRULE 표준 부분(`FREQ` 7가지) + 확장 키(`TK_COMPLETEDCOUNT`, `TT_SKIP`, `TT_WORKDAY`), 날짜 직접 선택은 `ERULE:NAME=CUSTOM;BYDATE=…` (§5.9.1). 서버는 형식만 검사하고 뜻은 해석하지 않는다.
- `next_occurrence_at` 은 클라이언트가 계산해 쓰는 값이다 (§7.6, 1장 전제).
- `priority` 값은 0·1·3·5 (§4.5 [확인]). 검사 제약을 건다.
- 종일 할 일: 하루짜리는 `due_local` 이 null 이다 [확인]. 여러 날이면 마지막 날 다음 날 00:00 〔바뀔 수 있음: §4.5 [추정]〕.
- `deleted_at` 은 서버 기록용이다 (spec.md §4.5 (새로 정함)). 휴지통 정렬은 `updated_at` 내림차순이다 〔바뀔 수 있음: §5.11.8 [추정]〕.
- 인덱스: (`user_id`, `list_id`, `status`) 휴지통 제외, (`user_id`, `deleted_at`) 휴지통만, (`user_id`, `updated_at`) 휴지통 정렬, (`user_id`, `completed_at`) 완료만, (`user_id`, `start_local`), (`user_id`, `changed_at`), `tags` GIN.

## 3. 행 단위 보안 (RLS) (새로 정함)

| 대상 | 규칙 |
|---|---|
| 사용자 데이터 테이블 전부 | 읽기·쓰기·지우기 모두 `user_id = 로그인 사용자`. **목록에 딸린 테이블(`lists`·`tasks`·`checklist_items`·`attachments`·`sections`·`comments` 등)은 11.3 의 목록 권한 규칙으로 바뀐다** |
| 자식·참조가 있는 쓰기 | 넣거나 고칠 때 **가리키는 행도 내 것인지** 확인한다: `tasks.list_id`·`parent_id`, `checklist_items.task_id`, `attachments.task_id`, `focus_records.task_id`, `focus_segments.record_id`. 외래 키 검사는 RLS 를 보지 않기 때문이다 |
| `entitlements` | 내 행 읽기만. 쓰기는 R15 로만 |
| `plan_limits` | 로그인 사용자 읽기만 |
| `deletions` | 내 행 읽기만. 트리거만 쓴다 |
| 저장소 버킷 | 비공개. 경로 = `{user_id}/{task_id}/{attachment_id}`. 첫 폴더가 내 ID일 때만 올리기·읽기·지우기 |
| RPC | 모두 **호출한 사용자 권한으로 실행**한다. 그래서 RPC 안에서도 RLS 가 그대로 걸린다. 예외는 가입 트리거(T8), 묘비 트리거(T9), Pro 스위치(R15, 내 `entitlements` 행 하나만 바꾼다) 셋이다 |

## 4. 트리거 — 한 행 안에서 끝나는 검사 (새로 정함)

한 행만 보고 판단할 수 있는 검사는 일반 쓰기에 트리거로 붙인다. 오류는 spec.md §7.1 의 오류 코드를 메시지로 올리고, 클라이언트가 그 코드로 안내를 고른다. 한도 값은 내 `entitlements.plan` 으로 고른 `plan_limits` 행에서 읽는다.

| # | 대상 | 하는 일 | 근거 |
|---|---|---|---|
| T1 | 모든 테이블 | `changed_at` 갱신, `version` 증가, `updated_at` 갱신(RPC 가 막으라고 표시한 경우와 접힘만 바꾼 경우 제외) | §7.1, §5.9.8, §4.5 |
| T2 | `tasks` 쓰기 | 휴지통·보관(닫힌) 목록 할 일 수정 막기. 단 휴지통 복원(삭제 표시만 끄는 수정)은 통과 | §5.1, §5.11.4, §7.6 |
| T3 | `tasks` 쓰기 | 본문 줄바꿈 정리, 시작일이 비면 알림 비우기, 할 일당 알림 수 한도(무료 2, Pro 5), `repeat_rule` 형식 검사(§5.9.1 의 RRULE·확장 키·`ERULE`). 제목은 검사하지 않는다 〔바뀔 수 있음: §5.2 앱에서 확인 필요〕 | §5.2, §5.10.1, §5.10.3, §5.9.1, §7.6 |
| T4 | `tasks` 넣기·부모 바꾸기 | 하위 깊이 검사(부모를 바꿀 때는 하위 트리 전체) | §5.5, §7.6 |
| T5 | `tasks` 넣기·목록 이동·미완료로 되돌리기 | 목록당 **미완료** 할 일 수 한도. 받은편지함은 Pro 면 검사하지 않고, 무료면 Pro 한도값으로 검사 | §5.3, §5.11.5, §7.6 |
| T6 | `checklist_items` 넣기, `attachments` 넣기 | 체크리스트 항목 수 한도, 할 일당 첨부 수 한도(20), 무료 하루 업로드 1 〔바뀔 수 있음: 하루 한도를 검사하는 곳 §5.8 [미확인]〕 | §5.4, §5.8, §7.7 |
| T7 | `user_settings` 쓰기 | 집중 시간이 5분 미만이면 5분으로 보정. 상한은 두지 않는다 〔바뀔 수 있음: §5.14.4 앱에서 확인 필요〕 | §5.14.4, §7.4 |
| T8 | 가입(`auth.users` 넣기) | `profiles`, `entitlements`(free), `user_settings`(기본값), 받은편지함 목록을 만든다 | §6, F1 |
| T9 | 행을 실제로 지울 때 | `deletions` 에 묘비를 남긴다 | §7.11 |
| T10 | `lists` 지우기 | 받은편지함이면 막는다 〔바뀔 수 있음: §7.5 [추정]〕 | §7.5 |

## 5. 서버 함수 (RPC) — 원자적 저장 (새로 정함)

### 5.1 RPC 로 둘지 정하는 기준

- **두 행 이상을 함께 바꾸거나, 읽은 값으로 다른 행을 바꿔야 하면 RPC.** 중간에 끊기면 데이터가 어긋나기 때문이다.
- 한 행만 바꾸고 검사도 그 행으로 끝나면 일반 쓰기 + 트리거(4장).
- 공통 약속:
  - 대상 행의 기대 `version` 을 받는다. 다르면 `VERSION_CONFLICT` 와 현재 행을 돌려준다 (§7.1).
  - 새로 생기는 행(완료 사본, 나뉜 시리즈, 복제본 등)의 ID 도 **클라이언트가 만들어 넘긴다.** 그 ID가 이미 있으면 이미 처리된 요청으로 보고 저장된 결과를 돌려준다. 그래서 오프라인 대기열이 같은 요청을 다시 보내도 안전하다 (§7.1 멱등의 확장).
  - **반복 관련 RPC 는 계산하지 않는다** (spec.md §7.6 "반복 계산의 위치"). 클라이언트가 계산한 결과 행(옮긴 원본, 완료 사본, 하위 할 일 사본·되돌림, 체크리스트 변경, 새 규칙 문자열, 제외 날짜, `next_occurrence_at`)을 통째로 받아 한 트랜잭션으로 쓴다. 검사는 형식뿐이다: 소유자, `version`, ID 중복, 반복 할 일이 아닌데 반복 결과가 온 경우, 규칙 문자열·날짜 형식, 한도.

### 5.2 RPC 목록

| # | 이름 | 한 트랜잭션 안에서 하는 일 | 클라이언트가 넘기는 계산값 | 근거 |
|---|---|---|---|---|
| R1 | **할 일 상태 바꾸기** (완료·포기·되돌리기, 반복 포함) | 반복이 아니면 상태를 바꾸고, 클라이언트가 넘긴 하위 할 일도 함께 닫는다 〔바뀔 수 있음: 부모 완료 시 하위 처리 §5.5 [추정]〕. 반복이면 받은 결과(§5.9.7 의 두 경로: 원본 이동 + 완료 사본, 또는 제외 날짜 추가 + 완료 사본, 하위 할 일 완료 사본과 되돌림, 체크리스트 변경)를 그대로 쓴다. 포기도 같다 | `repeatResult`(옮긴 원본 값, 완료 사본 행, 하위 할 일 사본·되돌림 행, 체크리스트 행, `next_occurrence_at`), 함께 닫을 하위 할 일 ID | §5.5, §5.9.7, §5.11.5, §5.11.6, §7.6 상태 바꾸기 |
| R2 | **지난 회차 정리** (모두 완료 / 모두 건너뛰기) | 클라이언트가 N+1번 처리한 결과(완료 사본들 또는 건너뛴 회차, 옮긴 원본)를 한 번에 쓴다. "모두 건너뛰기"는 `COUNT` 를 유지한 결과가 온다 〔바뀔 수 있음: N+1 의 뜻, 건너뛰기와 `COUNT` §5.1, §5.9.3 [추정]〕 | `repeatResult`, 사본 ID 목록 | §5.1, F3, §7.6 지난 회차 정리 |

### 5.3 RPC 로 두지 않는 것

| 처리 | 방식 | 이유 |
|---|---|---|
| 할 일 만들기, "저장 후 새로 만들기" | 일반 넣기 + T3~T5. 바로 뒤 정렬 값은 클라이언트가 이웃 값 사이로 계산 | 한 행 (§5.3) |
| 할 일 수정(반복 아님, 또는 범위를 정하지 않는 수정), 자동 저장 | `version` 조건을 단 일반 수정. 0행이 바뀌면 충돌로 본다 | 한 행 (§5.2, §7.6) |
| 반복 할 일 날짜를 바꿀 때 규칙 다시 만들기 | 클라이언트가 새 규칙과 `next_occurrence_at` 을 계산해 일반 수정 | §5.9.4 날짜를 바꿀 때, §7.6 |

| 예정 목록 끌어 놓기 | 시작 = 놓은 날짜 00:00, 마감 없음, 종일로 일반 수정. 반복이고 범위가 모든 회차가 아니면 R3 | §5.12, §7.9 |
| 수동 정렬 저장 | `sort_orders` 여러 행 upsert 한 번 (한 요청은 원자적) | §4.10, §7.6 |
| 첨부 올리기 | 행 먼저 넣기(T6 한도 검사) → 저장소에 올리기 → 실패하면 행 지우기 | 한도를 올리기 전에 검사하려고 (새로 정함) |
| 설정 바꾸기 | `version` 조건 수정 + T7 | §7.4 |

## 8. 동기화 — 웹과 안드로이드가 같은 데이터를 보는 방식 (새로 정함)

### 8.1 결정

**기본은 "새로고침 기준"(변경분 당겨오기)이고, 실시간 구독은 "다시 당겨오라"는 신호로만 쓴다.**

- 실시간 구독만 믿으면 연결이 끊긴 동안의 변경을 놓친다. 당겨오기를 기본으로 두면 구독이 끊겨도 다음 당겨오기에서 맞춰진다.
- 구독 메시지의 내용을 화면에 바로 반영하지 않는 이유: 반복 완료(R1)처럼 한 처리로 여러 행이 바뀌면 메시지가 따로따로 와서 화면이 잠깐 어긋난다. 신호를 받으면 짧게 모았다가(예: 300ms) 한 번 당겨온다.

| | 웹 (B 웹, C Next.js) | 안드로이드 (B 안드로이드, C Kotlin) |
|---|---|---|
| 기준 | 온라인 우선. 화면 데이터 = 서버 조회 결과 캐시 | 로컬 DB 우선. 화면 데이터 = 로컬 DB |
| 당겨오는 때 | 앱 시작, 탭이 다시 보일 때, 화면 진입, 내 쓰기 뒤, 구독 신호 | 앱 시작, 앞으로 올 때, 구독 신호, 주기 작업(백그라운드), 네트워크 복구 |
| 실시간 구독 | 탭이 보이는 동안만 | 앱이 앞에 있는 동안만 |
| 쓰기 | 바로 서버로. 실패하면 화면 값을 되돌리고 안내 | 로컬에 먼저 쓰고 쓰기 대기열에 넣는다. 대기열이 순서대로 서버에 보낸다 |
| 알림 재예약 | 당겨온 뒤 탭 안 알림 다시 계산 | 당겨온 뒤 기기 알림 다시 예약 (웹에서 바꾼 알림이 안드로이드에 반영되는 길) |

B 가 웹에서도 로컬 DB 를 쓸지는 `B-flutter.md` 에서 정한다.

### 8.2 변경분 당겨오기 (spec.md §7.11 대응)

1. 테이블마다 마지막으로 받은 `changed_at` 을 커서로 기억한다.
2. `changed_at > 커서 − 겹침 시간`(예: 5초)인 행을 읽는다. 겹치게 읽는 이유: 트랜잭션이 커밋되는 순서와 `changed_at` 순서가 다를 수 있어서다. 같은 행을 두 번 받으면 `version` 이 큰 쪽만 남긴다.
3. `deletions` 도 같은 방식으로 읽어 로컬에서 지운다.
4. 휴지통 이동·완료 같은 상태 변화는 삭제 표시·상태 열이 바뀐 행으로 들어오므로 따로 처리하지 않는다.

### 8.3 충돌 처리 (spec.md §10 "병합 규칙")

- 감지: 일반 수정은 `version` 조건으로, RPC 는 기대 `version` 으로 (§7.1).
- 처리: 서버 행을 받고, **내가 바꾼 필드가 서버에서 바뀌지 않았으면 내 값을 다시 적용**한다. 같은 필드를 양쪽이 바꿨으면 서버 값을 두고 "다른 기기에서 바뀜" 안내를 띄운다.
- 자동 저장 중인 제목·본문은 예외로 내 값을 다시 적용한다(사용자가 지금 치고 있는 글을 잃지 않게).
- RPC 충돌(예: 다른 기기에서 이미 완료한 반복 할 일을 또 완료): 클라이언트가 서버 행으로 다시 계산해 한 번 더 보낼지 묻지 않고, 서버 상태를 보여 주고 안내만 한다.

### 8.4 두 플랫폼이 같이 정해야 하는 것 (spec.md §10 중) (새로 정함)

## 11. 확장 범위 — 협업과 확장 기능 (새로 정함)

spec.md §1 이 원본 기능 전부로 넓어지면서 바뀌는 서버 설계다. 규칙은 `spec-ext.md` 를 따르고 이 장은 "spec-ext 16.1" 식으로 가리킨다(아래 `ext` 는 spec-ext.md 의 절이다).

- **협업(ext 16장)의 서버 동작은 원본을 조사하지 않아 이 장에서 새로 설계했다** (spec-ext 19.1 G2). 화면과 앱 쪽 동작은 spec-ext 대로다.
- 외부 연동(ext 17장)은 "연결 안 됨"이라 서버에 만들 것이 없다 (G3).
- 반복·필터·습관 연속·디데이 같은 계산은 1장 전제대로 **클라이언트 공통 규칙 모듈**이 한다. 서버는 저장·권한·한도·알림 센터 행 만들기만 한다.

### 11.1 바뀌는 전제

| 1장 전제 | 바뀐 것 |
|---|---|
| 1인 사용 | 목록 공유·팀이 생긴다. 남이 내 목록의 행을 읽고 쓴다 |

| 서버는 사용자 사이 데이터를 모른다 | 초대·신청·담당자·댓글·회의는 다른 사용자에게 알림 센터 행을 만든다. 이 처리만 **정의자 권한**으로 돈다 (11.5) |

### 11.3 데이터 접근 규칙 (RLS) — 공유받은 목록·팀 멤버 권한

**판정 함수** (정의자 권한, 읽기 전용, 검색 경로 고정). 모든 정책이 이것만 부른다.

| 함수 | 돌려주는 것 |
|---|---|
| `list_role(list_id)` | 내 권한: 목록 `user_id` 가 나면 `owner` → 활성 `list_members` 행의 권한 → 목록에 `team_id` 가 있고 내가 활성 팀원이면 팀 `default_permission`(팀 소유자·관리자는 `owner`) → 없으면 null |
| `list_writable(list_id)` | `list_role` 이 owner·write 이고, 팀 목록이면 팀이 만료되지 않았고, 목록이 보관(닫힘)이 아님 |
| `task_role(task_id)` | 그 할 일의 목록으로 `list_role` |
| `shares_with(user_id)` | 그 사람과 같은 목록·팀·회의·스터디룸에 있는지 (프로필 보기용) |

**정책**

| 대상 | 읽기 | 넣기·고치기·지우기 |
|---|---|---|
| `lists` | `list_role` 이 null 이 아님 | 넣기 = 내 것. 고치기 = owner (이름·색·보관·보기 모드 등). 지우기 = R7 만 |
| `tasks`, `sections` | `list_role` 이 null 이 아님 | `list_writable` (휴지통 복원은 R5) |
| `checklist_items`, `attachments` | `task_role` 이 null 이 아님 | `task_role` 의 목록이 `list_writable` |
| `comments` | `task_role` 이 null 이 아님 | R24 만 |
| `list_members`, `share_links`, `list_join_requests` | 멤버는 그 목록의 멤버 행. 링크는 owner. 신청은 신청자와 owner | R16~R21 만 |
| `teams`, `team_members` | 그 팀의 활성 팀원 | R22 만 |
| `agendas`, `agenda_attendees` | 소유자와 참석자 | R25 만 |
| `activity_logs` | `task_role` 이 null 이 아님 | 트리거만 (T13) |
| `notifications` | 내 행 | 고치기 = 내 행의 `unread`·`deleted`·`action_status` 만 (열 권한). 넣기 = 트리거·정의자 RPC |
| `membership_events` | 내 행 | 트리거만 (T14) |
| `study_rooms` | 공개 방 전부 + 내가 든 방 | R26 만 |
| `study_room_members` | 공개 방·내 방의 멤버 | R26 만 |
| `referrals` | 초대한 사람·받은 사람 | R28 만 |
| `profiles` | 내 행 + `shares_with` 가 참인 사람의 `display_name` | 내 행 |
| `deletions` | `user_id = 나` 또는 `list_role(list_id)` 이 null 이 아님 | 트리거만 |
| 저장소 버킷 | 경로 첫 폴더를 **목록 ID** 로 바꾼다: `{list_id}/{task_id}/{attachment_id}`. 읽기 = `list_role` 이 있음, 올리기·지우기 = `list_writable` | 개인 목록도 같은 경로 규칙 |
| 그 밖의 개인 테이블 (`sort_orders`, `pins`, `user_settings`, `focus_records`, 습관·디데이·타이머·시간표 등) | 3장 그대로 `user_id = 나` | 같음 |

- 휴지통 읽기: 개인 휴지통 = 내가 owner 인 목록의 삭제 표시 할 일, 팀 휴지통 = 내가 팀원인 팀 목록의 삭제 표시 할 일 (ext 16.8). 둘 다 같은 `tasks` 정책 위에서 클라이언트가 고른다.
- 판정 함수가 정의자 권한이라 정책이 서로 부르며 돌지 않는다. 함수 안에서 `auth.uid()` 만 쓴다.
- 3장 표의 "자식·참조가 있는 쓰기" 검사는 "가리키는 행이 내 것"에서 "가리키는 행에 쓰기 권한이 있음"으로 바뀐다.
- 담당자(`tasks.assignee_id`)는 그 목록의 활성 멤버여야 한다 (T12).

### 11.6 실시간 동기화 — 바뀌는 것

8장의 "당겨오기가 기본, 실시간은 신호" 방식을 그대로 쓴다. 공유 때문에 생기는 빈틈 세 가지를 막는다.

| 빈틈 | 처리 |
|---|---|
| **새로 권한을 받은 목록**: 그 목록의 오래된 행은 `changed_at` 이 내 커서보다 앞이라 당겨오기에 안 잡힌다 | T14 가 `membership_events(granted)` 를 남긴다. 클라이언트는 이 표도 커서로 당겨오고, `granted` 를 보면 **그 목록 전체**(할 일·섹션·항목·첨부·댓글)를 따로 읽는다 |
| **권한을 잃은 목록**: 행은 지워지지 않아 묘비가 없고 RLS 로 안 보이게만 된다 | `revoked` 를 보면 로컬에서 그 목록의 행을 모두 지운다 |
| **남이 지운 공유 행** | 묘비에 `list_id` 를 넣어(T15) 멤버도 읽는다 |

- 실시간 구독 대상에 `comments`, `notifications`, `membership_events`, `list_members`, `focus_live`, `study_room_members` 를 더한다. 신호에는 ID 만 쓰고 데이터는 당겨오기로 읽는다(8.1). 실시간 서비스가 구독자마다 RLS 를 적용하는지는 1단계에서 두 계정으로 확인한다(플랫폼 문서 위험 표).
- 스터디룸의 "지금 집중 중"은 DB 가 아닌 실시간 접속 표시 채널(방마다 하나)로 보낸다. 접속 표시에는 사용자 ID 와 집중 상태만 싣는다.
- 기기 간 집중 동기화(ext 14.9)는 `focus_live` 행이 바뀌면 같은 사용자의 다른 기기가 신호를 받고 읽는다.
- 충돌(8.3)은 그대로다. 같은 할 일을 두 사람이 고치면 `version` 으로 감지하고, 다른 필드면 다시 적용, 같은 필드면 서버 값 + "다른 기기에서 바뀜" 안내를 "다른 사람이 바꿈"으로 바꿔 띄운다.
- 웹(온라인 우선)은 `granted`·`revoked` 를 받으면 캐시를 버리고 다시 읽기만 하면 된다.

### 11.7 한도 — `plan_limits` 에 더하는 열

seed 값은 원본 앱 기본값이다 (spec-ext "한도 모음"). 원본은 계정 종류에 팀 행이 따로 있고 섹션 한도는 늘 팀 행을 읽으므로 **`plan = 'team'` 행을 seed 에 더한다** (섹션 한도만 읽는다).

| `max_file_bytes` | 10 MiB | 20 MiB | — | [확인: 보조 도구(dexdump)]. 2.2 의 "첨부 크기 새로 정함"을 이 값으로 바꾼다 |
| `max_sections_per_list` | — | — | 39 | [확인: 보조 도구(dexdump)] |

| `max_timers` | 5 | 49 | — | [확인] |
| `max_countdowns` | 9 | 299 | — | [확인] |

| `max_teams`, `max_team_members` | 3, 999 | 3, 999 | — | 〔바뀔 수 있음: [추정]〕 |

- 공유 인원 한도는 **목록 소유자**의 행으로 본다 (ext 16.1).
